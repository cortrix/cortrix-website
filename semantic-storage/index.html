A practical guide

What is semantic storage?

Semantic storage organizes information together with the meaning, relationships, and source context an application needs to retrieve and use it.

This guide explains semantic storage as an architectural approach. The goal is to connect stored material with enough context for an application to find relevant information and inspect what it has found. Implementations can combine documents, structured records, vector or keyword indexes, and graph relationships in different ways.

Start with a question your data should answer

Imagine asking an agent why a deployment failed last week. A runbook describes the expected procedure. A ticket records an exception. A later note corrects the team's first diagnosis.

Finding a passage that resembles the question is useful, but it leaves other questions open. Does the passage describe this deployment? Is it still current? Can the agent follow the correction back to the original incident?

A semantic storage approach keeps those connections within reach. The application can retrieve material while retaining the identifiers and source information needed to check it. That is a design objective to evaluate, not an assurance that every retrieved answer will be correct.

What the system needs to keep

The source material remains important. A derived summary or embedding is useful in relation to the information it represents. The surrounding records can preserve a document's identity, its revision, and the passage an application actually retrieved.

Relationships add another route through the data. An entity can occur in several documents, and two records may refer to the same event. Stable identifiers help an application recognize that connection. Depending on the workload, relationships can be represented as ordinary record fields, explicit links, or a graph.

Retrieval indexes help select candidates. An application might combine a keyword match with an embedding score or use explicit relationships to follow a connection. The storage and retrieval design should keep a route back to the records those candidates came from.

How this relates to databases, RAG, and memory

These concepts address different parts of the workflow. A system can use several together.

ConceptWhat it focuses onHow it connects
DatabaseStoring and querying application records.A database can hold the source records, identifiers, and metadata used by a semantic storage layer.
Vector database or indexStoring embeddings and ranking candidates by vector distance or similarity.It is one retrieval method. The score alone does not establish identity, source quality, or whether a record is current.
RAGUsing retrieved external material during generation.It consumes evidence from an index or data layer. The application still needs to manage that external knowledge.
Agent memoryRetaining information or experience for a future interaction.Memory storage can use semantic retrieval, but relevance does not establish that an old memory is valid for a new task.

For example, a RAG application retrieves external material and uses it during generation. Its data layer has to keep that material current and preserve a way to inspect the sources. Choosing a retrieval method is one part of that design.

An agent memory system has a different responsibility: deciding what to retain for later use. A record of an earlier mistake may be useful, but it also needs enough context to show when that lesson applies.

Agent storage, context storage, and memory storage

These terms emphasize different needs within an application. Agent storage concerns the data read and written during a workflow. Context storage keeps material available for a particular model invocation. Memory storage retains information that may matter in later interactions.

The boundaries can overlap. A source passage retrieved as context today might inform a retained note for tomorrow. The useful question is what the application needs to preserve and check at each step, rather than which label it adopts.

What this approach does not solve on its own

Structure and retrieval do not make a source true. An extracted relationship can be wrong, a document can be outdated, and a model can draw a conclusion its evidence does not support. Keeping the evidence inspectable helps you investigate those problems; it does not remove the need for evaluation.

Access control, deletion, version handling, and memory review need explicit implementation and evaluation. A namespace label or a similarity score does not enforce those policies. Start with one realistic question and inspect the returned sources, then test what happens when the source changes or should no longer be used.

Where Cortrix fits

Cortrix is an open source project exploring semantic storage for retrieval, reviewable records, memory APIs, and source context. It is in active pre-release, and the maturity of each interface needs to be checked separately.

You can try a local Docker evaluation, inspect the architecture overview, or read the published retrieval benchmarks. Those results concern their stated retrieval tasks and measurement scope; they do not establish memory quality or production readiness.

Authentication, authorization, and production readiness are not established by this guide. The public evidence guide keeps the current source references and capability limits together.
