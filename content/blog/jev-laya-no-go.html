Jev and Laya, a third-party open-source model in the same category, have been getting a lot of attention this week. We looked at how they would fit into Cortrix and decided to leave them out for now.

I can see the appeal. Give Jev a piece of state and a few options, and it returns a typed decision—a Choice, a Score, or a boolean—with probabilities. That looks useful for tool selection, query routing, retry decisions, and scoring candidates. Plenty of systems need small, well-defined judgments like these.

But that isn't the main problem we're working on in Cortrix. We're building Semantic Storage for agents: organizing content as it keeps coming in, finding potentially relevant material when an agent asks for it, and returning the results with their sources, context, and retrieval trace.

The first hard part is getting the right material into the candidate set. Picking a winner comes later.

So we're not putting Jev at the center of retrieval just because it's this week's hot model.

A reranker can't find a document it never sees

TypeSafe describes Jev as a System One model: unstructured state goes in, typed probabilistic decisions come out, and it gives up text generation. That boundary is fairly clear. Jev doesn't produce embeddings, rewrite queries, generate summaries, or return other generated content.

A retrieval system still has to find candidates. Vector indexes, sparse indexes, keyword search, document discovery, and query expansion can all bring in a document that would otherwise stay invisible. Jev can score a document once it's there. Scoring the candidates you've already found cannot recover a different document that never made it into the set.

The set notation is simple. Call the initial candidates C_N and the final results S_k. If Jev only reranks, then:

S_k ⊆ C_N

It can change the top ten. It can't raise the recall ceiling imposed by the candidate set.

The public result is interesting, within its limits

We checked TypeSafe's reranking example, the public result closest to our use case. It uses 40 CLERC queries and 3,565 passages. BM25 retrieves 30 candidates per query, then Jev scores them. The report shows top-10 accuracy going from roughly 38% to 62%.

That's evidence that Jev can make useful judgments about retrieved candidates. It doesn't establish a new ability to retrieve missing documents. It also doesn't tell us whether Jev beats the local BGE setup we already use. Laya, the third-party open-source model, doesn't currently have enough public data to establish that either.

Independent public evaluations do not give us a reason to swap it in. jev-search-rerank-eval used 164 Chinese, English, and mixed-language queries with 9,831 labelled pairs. Jev reranking bge-m3's top 30 improved NDCG@10 by 0.012, with a 95% confidence interval from -0.013 to +0.037. Under labels produced without Jev, the result was -0.028. In a separate jev-orderby-bench Amazon ESCI hard probe, Jev failed four of six gates. Neither test is a Cortrix benchmark, but both show that Jev reranking is not a free replacement for the current path.

The request budget deserves a closer look, too. Jev's documentation lists a limit of 1,200 requests per minute. If we score 20 candidates separately for each query, we spend 20 requests on one application query. That gives us a theoretical ceiling of about one query per second, before routing calls, retries, or other tenants use any of that capacity.

Putting several candidates into a single request could reduce the request count. It would also change context length and potentially scoring consistency. We'd need to test that configuration separately rather than assume it behaves the same way.

Cheap tokens don't settle the cost question

Low input prices and structured output are attractive when all you need is a decision over a small set of options. But we have to pay for the whole pipeline: Jev calls, the generation model, networking, logging, retries, fallbacks, and calibrating the decisions.

Where the decision happens matters a lot.

If Jev can tell us before generation that a task doesn't need generated content, it might save an expensive model call. If we generate the content first and then ask Jev whether to throw it away, the LLM bill is already paid. We might still avoid embedding, indexing, or some later processing, but the savings are much more limited.

The component being replaced matters just as much. Replacing an expensive LLM judgment could help. Replacing a fast local rule adds a network call and latency to something that was already cheap. That could make the system slower.

A lower token price doesn't automatically mean a cheaper system.

We came away with three conclusions

We went through the places Jev might fit: embeddings, cross-encoder reranking, query-complexity routing, judging retrieval results, and memory extraction.

First, it can't replace embeddings. Jev doesn't return vectors. It can't do the job of building a vector index or retrieving nearest neighbors.

Second, we don't have evidence to replace local reranking. The public result gives us a reason to compare, not a reason to switch. Before replacing anything, we'd need BGE and Jev evaluated on the same candidate sets. We'd compare NDCG, Recall@k, p95 latency, throughput, behavior under failure and fallback, and total cost. We may include that comparison in a future benchmark round.

Third, bounded decisions could be useful. Routing, evidence tagging, deciding whether to run enrichment, and screening memory candidates are plausible places for Jev. We'd want it somewhere it can actually eliminate downstream work—for example, deciding whether to proceed before generation starts.

We'd also need to keep the existing path available when confidence is low, a request times out, or the service is unavailable. Adding a decision model must not turn a failed judgment into silently missed content.

This was an architecture review, not a benchmark

I want to be explicit about the evidence here: we have not benchmarked Jev or Laya in Cortrix.

We examined what Jev's interface can do, whether those capabilities change candidate retrieval, what its documented request limits imply for throughput, and how its inputs and outputs fit our existing components. That work did not establish a clear improvement for Cortrix. It also doesn't prove Jev would lose a head-to-head test. We haven't run one.

Jev is an interesting direction for model design. The hype doesn't change our decision: we aren't adopting Jev in Cortrix now, and we aren't starting a Laya evaluation.

If we revisit this, we'll put it into the same benchmark suite as BGE and our existing reranking methods, using identical candidate sets. Quality, latency, throughput, and total cost all have to be part of that comparison. We'll consider adopting it when those results show that it actually improves Cortrix's retrieval pipeline.

For now, our job is still to find the right content for an agent and give it the sources, context, and retrieval trace to work with. A week of Jev hype hasn't changed that.
